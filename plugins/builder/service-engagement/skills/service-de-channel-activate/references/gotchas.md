# Gotchas

1. **PATCH is synchronous with Meta `/register` for WhatsApp.** Expect 15-30s response times. Don't set an HTTP client timeout below 60s. The observer runs post-commit but before the HTTP response headers ship — the 204 is the "it all worked" signal. This is why a WhatsApp channel inserted by `service-de-channel-create` takes noticeably longer to activate than an Apple or LINE channel, which have no external callout.

2. **Valid API status transitions are gated by `ChannelUsageDeploymentStatusEnum.getValidAPIStatusTransitions()`.** From `Disabled` or `New`, only `Provisioning` is allowed. From `Error`, `Provisioning` (retry) or `Deprovisioning` (give up). From `Active`, only `Deprovisioning`. The DB-only transitions (`Provisioning → Active|Error` and `Deprovisioning → Disabled`) cannot be written by a client — that's the server's job. Don't try to shortcut by PATCHing `Active` directly; the validator returns 400.

3. **The second save-hook fire that flips `IsActive` runs in the same observer, not as a separate request.** Inside `MessagingChannelUsageFunctionsHelper.handlePostSave`'s TransactionObserver, after the PLSQL status write, a second pass iterates `messagingChannelObjectsToUpdate` and flips `IsActive` via `setBypassingIsActiveGate(true)`. So one PATCH produces a fully-activated channel — no second client call needed.

4. **`MessagingChannelId` is the FK name on MCU, and the parent-to-child relationship name varies across orgs.** On `test1`, `MessagingChannel` has child relationship `MessagingChannelUsages` (plural) so `(SELECT ... FROM MessagingChannelUsages)` works. On `wadtesting`, the child relationship is `None` (unnameable) and the same subquery errors `INVALID_TYPE`. Stage 1 uses two FK-keyed queries to sidestep the variance — don't collapse them back into a subquery.

5. **Consent configuration is a precondition validator.** For WhatsApp, `validateChannelReadinessOnProvisioning` requires STOP/HELP keyword consent. If not configured, PATCH fails with `FIELD_INTEGRITY_EXCEPTION` at `validateBeforeSave` time (before the observer even runs). The old Apex method hit the same validator — this isn't a regression. If a caller sees `kind:"readiness-failed"` with a consent message, the fix is either configure consent in Setup → Messaging Settings or programmatically via `MessagingConsentConfig` — not the activation skill's concern.

6. **`DeploymentStatus` picklist values are PascalCase.** Specifically `Provisioning`, `Active`, `Error`, `Disabled`, `Deprovisioning`, `New`. Case-sensitive — `PROVISIONING` fails. The values are defined in `ChannelUsageDeploymentStatusEnum` and reflected in the sobject picklist metadata.

7. **The REST PATCH is equivalent to the old Apex `activateChannelUsage` method** but without the Aura session machinery or the quirk where that method returned `isSuccessful:false` with a misleading error even on success.

8. **If the observer fails partway, the MCU can land on `Error` with `ErrorReason` populated.** Common values for WhatsApp: `ProvisioningError` (Salesforce Admin API rejected — typically "Status code = 409" means phone already registered to another org; see gotcha #11), `MetaRegistrationFailed` (Meta `/register` rejected the phone — could be rate limit, PIN not set, WABA not shared, or credit line not attached), `NotAuthorized` (WABA partnership hasn't propagated). The `ErrorDetails` column carries the raw error response (Salesforce Admin API or Meta Graph API depending on where it failed). Don't swallow these — pass through to the caller's `provisioning-error` envelope.

9. **`ErrorReason === "VERIFICATION_REQUIRED"` means phone number needs OTP verification.** When activation fails with this specific ErrorReason on the MessagingChannelUsage, the skill should automatically proceed to Stage 3.2 (WhatsApp verification flow) rather than returning a generic provisioning-error. This is a recoverable error state that we can handle programmatically via the Connect REST verification endpoints. After successful verification, retry activation once (Stage 3.2 Step 5). Live-validated on headless-sdb6 2026-05-21 — verification request → SMS code entry → validation → retry activation succeeded in ~1 minute total.

10. **Auth stays inside the CLI transport — use `sf api request rest`, not a manually-extracted bearer token.** The skill used to extract an OAuth token via `SF_TEMP_SHOW_SECRETS=true sf org display` + `jq -r '.result.accessToken'` and pass it as an `Authorization: Bearer` header to `curl`. That pattern put a live access token into shell state (visible in process lists, shell history, and any logging) and was removed as an S1 security anti-pattern. `sf api request rest --target-org '{ORG_ALIAS}'` manages the same OAuth session internally and never surfaces the token to the shell. Historical note: the old pattern's failure mode — omitting `SF_TEMP_SHOW_SECRETS` left the token field null, which surfaced as a 401 `INVALID_AUTH_HEADER` — no longer applies now that the CLI handles auth end-to-end.

11. **`ErrorDetails` containing "Status code = 409" comes from the *Salesforce* Admin API, not Meta.** When `ErrorReason = "ProvisioningError"` with `ErrorDetails = "AdminApiRegistrationError__Error occured in admin api with error code  and error message Channel Registration response from Admin Api is a failure. Status code = 409"`, this indicates the phone number is already registered to a *different Salesforce org*. The Salesforce Admin API enforces a global constraint: one phone number can only be registered to one org at a time. To resolve: deactivate and deregister the phone from the other org, or use a different phone number for this org. This is distinct from Meta's validation errors (which would appear with `ErrorReason = "MetaRegistrationFailed"` and carry Meta Graph API error codes in `ErrorDetails`).
