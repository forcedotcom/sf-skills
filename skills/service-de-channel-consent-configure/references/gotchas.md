# Gotchas

1. **The activation-readiness contract lives in `MessagingChannelReadinessChecker.isConsentConfiguredForChannel`.** This is the authority — the UI (`channelRecordHome.js`, `languageOptionsModal.js`) mirrors it but is advisory. The three validators are:
   - `checkIfChannelIsConfiguredForImplicitOptIn`: at least one `MsgChannelLanguageKeyword` with `OptOutKeywords != null && OptOutConfirmation != null`.
   - `checkIfChannelIsConfiguredForExplicitOptIn`: implicit rule **plus** `OptInKeywords != null`, **plus** on the channel `(OptInPrompt != null || isUnifiedSMSOrWhatsappOrRCS)`.
   - `checkIfChannelIsConfiguredForDoubleOptIn`: explicit rule **plus** `DoubleOptInKeywords != null`, **plus** on the channel `DoubleOptInPrompt != null`.
   Consent is ANDed with routing in `isChannelReadyForActivation` — a channel with perfect routing still fails activation if consent is unmet.

2. **ImplicitOptIn is NOT a no-op.** The common misconception is that "implicit" means "nothing to configure." It still requires a `MsgChannelLanguageKeyword` record with opt-out keyword + opt-out confirmation. A channel set to `ConsentType=ImplicitOptIn` with zero keyword records fails the readiness check. This is the single most likely reason a freshly-configured channel won't activate.

3. **Outbound-only channels pass consent automatically.** `isOutboundOnlyChannel` short-circuits `isConsentConfiguredForChannel` to true. Don't try to configure consent on an outbound-only channel — there's nothing to satisfy, and the skill's "When NOT to use" section bails on this case.

4. **Keywords are comma-separated strings, not picklists.** Store `OptOutKeywords` as `STOP,UNSUBSCRIBE,CANCEL`. The server splits on comma and trims. A JSON array or newline-separated value will not match correctly. See `references/language-keywords.md`.

5. **One `MsgChannelLanguageKeyword` record per (channel, language).** Don't create a second record for a language that already has one — PATCH the existing record. Duplicate language records are ambiguous for the readiness check (it only needs *one* satisfying record, but duplicates make the UI and future edits inconsistent).

6. **`OptInPrompt` is exempt from the readiness check on Unified SMS / WhatsApp / RCS.** `isUnifiedSMSOrWhatsappOrRCS` makes `OptInPrompt` optional for the ExplicitOptIn/DoubleOptIn readiness rule. For all other channel types, `OptInPrompt` is required for ExplicitOptIn and DoubleOptIn. Note: `DoubleOptInPrompt` has NO such exemption — it is always required for DoubleOptIn regardless of channel type. **Detecting the exemption from a query:** there is no `IsUnifiedMessagingEnabled` column on the Data-API `MessagingChannel` sObject (verified via `sf sobject describe` on sdb6c 2026-08-13 — the queryable surface is `MessageType`, `PlatformType`, `MessagingPlatformKey`). Use `PlatformType='Enhanced' AND MessageType IN ('Text','WhatsApp','Rcs')` as the proxy for `isUnifiedSMSOrWhatsappOrRCS`. `MessageType` picklist values on this org include `Text`, `WhatsApp`, `Rcs`, `Facebook`, `AppleBusinessChat`, `EmbeddedMessaging`, `Line`, etc.

7. **Unified SMS adds two mandatory keyword-record rules.** Only when the channel is Unified SMS: `HelpKeywords`+`HelpResponse` become mandatory, and a `fr_CA` record additionally needs `CustomKeywords`+`CustomResponse`. These are enforced by the readiness check for Unified SMS and are irrelevant (optional) on WhatsApp/Facebook/etc.

8. **Consent applies to Enhanced channels only.** The UI gates the consent panel with `consentSettingsEnabled = platformType === 'Enhanced' && supportedMessageTypes.includes(messageType)`. On a Standard channel these fields are unused. Stage 1 confirms `PlatformType=Enhanced` and emits `kind:"not-enhanced"` otherwise.

9. **Legacy `OptInResponse` / `OptOutResponse` on `MessagingChannel` are deprecated (API 224).** Do NOT write them — the modern surface is `ConsentType` + `OptInPrompt` + `DoubleOptInPrompt` on the channel, and the per-language responses on `MsgChannelLanguageKeyword` (`OptInConfirmation`/`OptOutConfirmation`). The readiness check does not read the legacy fields.

10. **Switching ConsentType down should null the now-unused prompts.** The UI nulls `OptInPrompt` and `DoubleOptInPrompt` when moving to ImplicitOptIn, and nulls `DoubleOptInPrompt` when moving to ExplicitOptIn. If you re-run this skill to *lower* a channel's consent level, follow the same discipline so stale prompt text doesn't linger — though leaving them set does not fail the readiness check, it misrepresents the channel's configuration.

11. **WhatsApp channels with rich content reject `ExplicitOptIn`.** Setting `ConsentType=ExplicitOptIn` on a WhatsApp channel that has rich content is rejected server-side with `INVALID_INPUT: Consent Type for WhatsApp Messaging Channel with rich content cannot be set to EXPLICIT_OPT_IN` (verified live on sdb6c 2026-08-13). WhatsApp rich-content channels are effectively `ImplicitOptIn`. If the user asks for ExplicitOptIn/DoubleOptIn on such a channel, surface this constraint rather than retrying — emit `kind:"channel-patch-failed"` with the server message. Not all message types accept all ConsentTypes; the server is the authority.

12. **The `sf data ... --values` quoting rule is load-bearing.** The CLI tokenizes `--values` on spaces, so every multi-word value (all prompts, all confirmation messages) must be single-quoted *inside* the double-quoted `--values` string: `OptInPrompt='Reply YES to receive messages'`. Unquoted, it fails before hitting the server with `Malformed key=value pair for value: <second word>` (verified live). Keyword CSVs without spaces (`OptOutKeywords=stop,unsubscribe`) don't need quoting. To null a prompt when down-switching ConsentType, pass `OptInPrompt=''` — verified to set the field to null.

13. **`ConsentType` requires minApiVersion 224.** All consent fields (`ConsentType`, `OptInPrompt`, `DoubleOptInPrompt`, `IsRequireDoubleOptIn`) and the `MsgChannelLanguageKeyword` entity were introduced in API 224. The skill declares `minApiVersion: "67.0"` (well above 224); on an older org the fields won't exist and the Stage 1 query will error.

14. **Write `MsgChannelLanguageKeyword` over the regular Data/SObjects API — NOT the Tooling API.** `sf data create/update record --sobject MsgChannelLanguageKeyword` (the path this skill uses) works and is the sanctioned write path — verified live on sdb6c 2026-08-13: a `sf data update record` returned `success=true` at API v69.0, and `sf sobject describe` reports the object `createable: true, updateable: true`. **The entity XML is misleading here.** `MsgChannelLanguageKeyword.entity.xml` is a `setupEntity` carrying `<perApiAccess minApiVersion="246" apiAccess="isDevInternal || isUiTier" sobjectFamily="TOOLING"/>`. That block reads like a blanket write gate, but `sobjectFamily="TOOLING"` scopes it to the **Tooling API family only** — `ApiDictionaryInitializer._getFieldAccessStrategy` selects the `TOOLING` `perApiAccess` seed exclusively when `apiFamily.isTooling()`, so a regular SObjects/Data API request never applies it and instead uses the entity's base `createAccess`/`editAccess` (`LiveMessage.userCanCustomizeSetup`, which a setup-capable admin satisfies). Consequently a **Tooling** API write (`sf ... --use-tooling-api`, or the Tooling REST/SOAP endpoints) returns `NOT_FOUND` for this entity for external callers, while the Data API write succeeds. If a keyword write fails, first suspect a transient org issue (sdb6c 503 maintenance windows produced spurious `UNKNOWN_EXCEPTION` on Data-API writes during testing) and retry — do NOT switch to the Tooling API thinking it's the "real" write path; it isn't.
