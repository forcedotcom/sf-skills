# Gotchas — edge cases

Lower-frequency gotchas moved out of the core `gotchas.md` table to keep it scannable. Same
resolution format, just less common in a typical run.

| Issue | Resolution |
|-------|------------|
| Linked course naming pattern is not reliable | Always request a mapping file if user selects "linked courses" option |
| Existing courses have enrollments | Warn user that updating courses with active enrollments may impact students — offer to skip instead |
| User provides incomplete data and wants to proceed | Explicitly confirm with user: "5 courses will be created without descriptions. Proceed?" |
| Bulk import creates thousands of records under default Private sharing, or Person Accounts is enabled without the running profile having record-type visibility | Not this skill's job to change sharing/security settings, but flag it once at the end of the run: recommend the user (or an admin) review OWD/sharing rules and record-type visibility on the objects just populated, since a large private-shared import can be invisible to other admins/agents |
| describe pulls the full object schema (tens of KB) just to check one field's picklist values | Call describe once per object per run and cache the result (picklist values, createable fields) for reuse across every subsequent lookup on that object instead of re-describing per field/record |
| A subject code's department/account mapping is ambiguous (shared prefixes, courses left in the catalog from a retired program) | Before guessing or asking the user to correct it round-by-round, cross-check every ambiguous mapping in one pass: the source document, the institution's live public catalog if one exists, and course level/number patterns (e.g. HRM vs. general Business) — surfacing all ambiguous cases together with your proposed resolution up front costs one round of user review instead of several |
| Running user can't see records/values just created (recurring pattern — reported across multiple test sessions, not unique to this skill) | Metadata creates (new field, object, record type, or a picklist value on a record-type-scoped business process) don't auto-grant visibility to any profile. Resolve the running user via `GET /services/data/vXX.X/` → parse the `identity` URL's trailing `/<userId>` → `SELECT ProfileId, Profile.Name FROM User WHERE Id = '<userId>'`. Then check the relevant grant for what changed: a new/changed field → `FieldPermissions`; a record type touched (e.g. Person Account enabled in a prior session) → `RecordTypeVisibility`; a new object → `ObjectPermissions`. Name the exact gap and profile, offer the specific fix, and wait for confirmation before writing `Profile`/`PermissionSet` metadata — it's profile-wide, not scoped to this run |
| Adding a picklist value fixes the *global* value set but not necessarily every record type's available values | If the picklist field is record-type-scoped (a business process / per-record-type value set), a newly added value may still be unavailable on record types that existed before the value was added. Check record-type-specific availability, not just the field's global `restrictedPicklist` value list, before declaring the fix complete |
| Agent stalls indefinitely (no error, no progress) on ANY shelled-out org call — an ad hoc existing-record check (e.g. "check which CipCodes already exist"), or fetching org credentials via "sf org display" to hand-roll direct REST/Composite calls | Some agent surfaces show a manual "approval needed even in bypass" gate for any shell command containing `$(...)`, backticks, brace expansion, pipes into `python3`/`jq`, or eval — a gate that cannot be auto-approved and has no timeout of its own. Never shell out (CLI + command substitution, or CLI piped into a parser) for org lookups or credentials, even as a "faster" alternative to the MCP dispatch tool; use the headless-360 dispatch tool's SOQL `/query` or a direct REST read instead — same result, no approval gate, no CLI dependency |
