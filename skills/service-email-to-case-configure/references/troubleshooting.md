# Email-to-Case — Troubleshooting

Full symptom → resolution table for `apply-casesettings.py` and the dispatch calls it
drives. Read this when the apply or verify step reports an error, or when configured settings don't behave as expected.

| Issue | Resolution |
|-------|------------|
| Routing address fails on a fresh org with a single write | Use the two-phase flow from `apply-casesettings.py` — Phase A enables the toggles, Phase B adds addresses. One combined write (or a file-based `sf project deploy`) cannot provision addresses from scratch. |
| Phase B fails: "We couldn't save your routing address... custom email services named EmailToCase" | The On-Demand email service was not provisioned. This happens if the On-Demand toggle was set with a minimal field-level patch instead of writing the complete `emailToCase` block. `apply-casesettings.py` writes the full `emailToCase` block in Phase A specifically to provision it; do not reduce the write to a minimal patch. |
| Apply fails: "The setup requirements for Case Feed Items has to be enabled" | Only happens if the payload includes top-level Case Feed fields (`enableCaseFeed` etc.), which the platform re-validates against Chatter. `apply-casesettings.py` strips all top-level fields it does not own, so it should never hit this. If you see it, confirm the script's `KEEP_TOP_LEVEL_FIELDS` set hasn't been widened to include Case Feed fields. |
| `--routing-email` count doesn't match the addresses | The script exits non-zero without building a write. Provide exactly one `--routing-email` per routing address, in the order they appear in the source file. |
| Platform rewrites `routingName` to equal `emailAddress` | Expected for `EmailToCase` addresses. The verify read will show `routingName` == the supplied email; this is the platform's behavior, not an error. |
| Apply fails: "not an active User" / "not a Queue" / "not valid" for owner or automated user | The value the user supplied doesn't exist in the org (or the type is wrong). This is intentional fail-closed behavior — tell the user the value is invalid, ask for a valid Username / Queue DeveloperName / type, and re-run. Do not substitute a guessed user. |
| Apply/validate fails: "caseOwner is still the placeholder" or "sets caseOwner without caseOwnerType" on a routing address | A per-address Default Case Owner was left half-filled. Either supply a real value **and** its `caseOwnerType` (`User`/`Queue`), or remove both `caseOwner` and `caseOwnerType` from that address to fall back to the org Default Case Owner. The per-address owner is opt-in — omit it unless the user asked for a specific owner. |
| Support settings unexpectedly unchanged | The org already had a Default Case Owner + Automated Case User, so they were preserved (`supportSettings.action: preserved-existing`). Pass `--overwrite-support-settings` only if the user explicitly wants to replace them. |
| `check-write` reports `INVALID_FIELD ... Email to Case has be enabled to set EnableDraftEmails` | `enableDraftEmails` was sent before Email-to-Case was on. It must go in the same Phase A write as the enable flags, never alone. |
| `check-write` reports `UNKNOWN_EXCEPTION` (HTTP 500) with "couldn't save your routing address" | Same cause as the Phase B provisioning row above: Phase A did not carry the complete `emailToCase` block. Re-run from `phase-a` with a fresh read. |
| `phase-b` exits: "--current does not show enableEmailToCase/enableOnDemandEmailToCase enabled ..." | The `--current` read was taken before Phase A landed, so `phase-b` refused and built no write. Re-read with `requests settings`, dispatch it, save the response, and re-run `phase-b` with that fresh file. |
| A call returns `400 UNSUPPORTED_OPERATION: MetadataCrud does not support <VERB> on type: ...` | That verb is not enabled for the type on this route. `CaseSettings` read and update are supported; do not try other verbs or types as a workaround. Report the message to the user. |
| Requested address is `GmailOAuth` but org already has one | `GmailOAuth` connectors conflict; do not stack a second. Confirm the existing connector before adding. |
| `verify` fails with "The org did not keep these Support Settings even though the write reported success" | The org accepted the write (200) but did not persist the value, e.g. a named Automated Case User that is not eligible. Pick a different user, or use `useSystemUserAsDefaultCaseUser`. `verify` needs the same support/lookup flags as `phase-a`. |
| `Missing caseOwner` or "emailAddress is not available for an Outlook routing address" | `Outlook` addresses take no `emailAddress` and require `caseOwner` + `caseOwnerType`. Do not pass a `--routing-email` for them. |
| `GmailOAuth` address returns HTTP 500 `UNKNOWN_EXCEPTION` | Seen on a test org even with owner set; the connector likely needs an authorized Gmail account that dispatch cannot complete. Report it; do not retry in a loop. |
| Re-sending an existing `Outlook` address changes its `emailServicesAddress` | The platform regenerates it for Outlook (not `EmailToCase`). The script skips addresses that already exist; do not re-send them. |
| `E2cEasy` requested via Metadata | Not supported by the Metadata API — direct the user to the Service Easy Setup wizard. |
| New address doesn't receive production mail | For `EmailToCase`, the customer must verify the Salesforce-generated forwarding address out-of-band; `isVerified` is read-only and set by that flow, not by the apply. |
| Dispatch call fails (not connected, unauthorized, or `401`) | The org session belongs to the project-codey MCP server, not the skill. Have the user reconnect it (`/mcp`) or re-authenticate the org it is bound to; do not fall back to the `sf` CLI or a hand-built token. |
| Apply exits: "Target org appears to be PRODUCTION" | The safety gate fired. Confirm with the user that they intend to configure Email-to-Case on this production org (it's permanent), then re-run with `--confirm-production`. Do not add the flag without asking. |
| Apply exits: "Could not determine whether this is a production org" | The `Organization` row wasn't readable, so the org type is unknown and the script refuses to proceed; `--confirm-production` does not override this. Have the user reconnect or re-authenticate the org the dispatch server is bound to so the `Organization` row is readable, then re-run `gate`. |
| `cases` exits non-zero: "No Cases with Origin='Email'" | The inbound test email hasn't been processed yet, the routing address isn't verified, or `--supplied-email` excludes it. The check looks back over `LAST_N_DAYS:3`, so a test email older than that window won't match — send a fresh one. Confirm the user actually sent the email, wait a moment, and re-run. |
| `cases` finds a Case but no incoming `EmailMessage` | The Case may have been created another way (not inbound email). Re-run once the inbound email has been processed; proof requires `Incoming=true` linked to the Case. |
| "Enable Email Drafts" toggle silently ignored | The element name is `enableDraftEmails` (plural) and lives at the **top level** of `CaseSettings`, not inside `emailToCase`. A singular name or wrong container is ignored by the platform. |
| An `emailToCase` toggle doesn't take effect | Confirm it belongs in the `emailToCase` section, not top-level. `enableHtmlEmail`, `notifyOwnerOnNewCaseEmail`, `enableE2CDeduplicateAttachments`, and `showWordCountInComposer` are all `emailToCase` children; check the `verified.emailToCase.<field>` value in the JSON summary. |
